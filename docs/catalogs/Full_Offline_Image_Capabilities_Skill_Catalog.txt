Catalog edition: November 2026

Purpose and Scope

This document is a planning catalog for future reusable skills. It does not implement the listed skills or include model weights. Each entry is scoped so a stronger agent can convert it into a standalone skill or coordinated module. The target environment is fully offline or air-gapped, with local model files, pinned runtimes, reproducible prompts, explicit licenses, clean-sandbox tests, and recipient-ready packaging.

Design Principles for Future Skill Builders

- Pin models, encoders, tokenizers, VAEs, schedulers, LoRAs, packages, GPU runtimes, configurations, and presets by exact version and checksum.

- Default to no-download execution. A missing local component must fail clearly instead of silently reaching the internet.

- Preserve prompts, negative prompts, seeds, samplers, dimensions, controls, references, model versions, and output provenance.

- Treat generated images as candidates until decode, dimension, alpha, artifact, text, face, hand, consistency, color, rights, and visual checks pass.

- Use memory-aware fallbacks such as quantization, offload, attention slicing, tiling, smaller models, or CPU execution without hiding quality changes.

- Sandbox untrusted model files, archives, scripts, and dependencies and prefer SafeTensors or other non-executable formats where supported.

- Package the stack so another offline workstation can install, self-test, generate, edit, validate, repair, and continue the work.

Recommended Catalog-to-Skill Package

When converting an entry into an executable skill, keep the control file compact and place deterministic detail in supporting resources:

- SKILL.md: precise trigger description, workflow, decision rules, permissions, resources, failure conditions, validation, and completion behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic local generation, editing, inpainting, segmentation, upscaling, validation, packaging, diagnostics, and recovery tools.

- references/: model compatibility, runtime matrices, prompt standards, GPU budgets, quality rubrics, licenses, security rules, and troubleshooting.

- assets/: permitted presets, configurations, test prompts, masks, control maps, reference images, fixtures, and expected outputs.

Final Acceptance Standard

A future implementation should be considered complete only when it installs and runs without network access, loads all required local model components, respects hardware limits and rights, reproduces outputs from recorded settings, passes structural and visual quality checks, survives tested failures, and can be installed, self-tested, used, repaired, and continued from the complete offline package.
