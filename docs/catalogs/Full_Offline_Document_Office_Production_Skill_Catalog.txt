Catalog edition: November 2026

Purpose and Scope

This document is a planning catalog for future reusable skills. It does not implement the listed skills. Each entry is scoped so a stronger agent can convert it into a standalone skill or coordinated module. The target environment is fully offline or air-gapped, with native office structure preserved, repeatable rendering, cross-application compatibility, accessibility, secure signing, archival validation, and clean-state handoff.

Design Principles for Future Skill Builders

- Preserve native DOCX, PDF, PPTX, XLSX, OOXML, forms, formulas, revisions, tags, signatures, and accessibility structure whenever the recipient requires editability.

- Render and inspect final pages, slides, sheets, charts, and print layouts. Successful file creation alone is not proof of correctness.

- Test documents in Microsoft Office, LibreOffice, independent PDF renderers, target printers, and assistive technology where required.

- Pin fonts, templates, converters, OCR models, renderers, certificate chains, macros, codecs, and dependencies by exact version and license.

- Sandbox macros, VBA, scripts, active content, untrusted PDFs, archives, and imported documents before privileged access.

- Use checks that can fail for accessibility, formulas, charts, forms, signatures, encryption, conversion, print layout, and clean-room reopening.

- Block release on critical corruption, font, layout, calculation, accessibility, signature, redaction, privacy, or package-completeness defects.

Recommended Catalog-to-Skill Package

When converting an entry into an executable skill, keep the control file compact and place deterministic detail in supporting resources:

- SKILL.md: precise trigger description, workflow, decision rules, permissions, failure conditions, validation, and completion behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic offline rendering, conversion, calculation, comparison, OCR, validation, signing, redaction, packaging, and recovery tools.

- references/: OOXML rules, PDF standards, accessibility criteria, formula behavior, compatibility matrices, print specifications, license guidance, and troubleshooting.

- assets/: permitted templates, fonts, sample forms, test files, reference renders, certificates, fixtures, and evaluation documents.

Final Acceptance Standard

A future implementation should be considered complete only when it installs and runs without network access, preserves required document structure, renders correctly, recalculates formulas, validates accessibility and signatures, survives cross-format and cross-application tests, protects sensitive content, records provenance, and can be opened, edited, printed, converted, verified, and continued from a clean offline package.
