Catalog edition: November 2026

Purpose and Scope

This document is a planning catalog for future reusable skills. It does not implement the listed skills. Each entry is scoped so a stronger agent can later convert it into a standalone skill or coordinated module. The target environment is fully offline or air-gapped, with mirrored dependencies, reproducible builds, local data services, deterministic tests, explicit security checks, and clean-room validation.

Design Principles for Future Skill Builders

- Pin runtimes, compilers, packages, model weights, datasets, schemas, tools, and operating-system dependencies by exact version and hash.

- Prefer hermetic, repeatable, testable builds and local repositories over hidden global state or network downloads.

- Treat source, data, infrastructure, database, and scientific outputs as versioned artifacts with provenance and rollback.

- Use checks that can fail: compilation, unit and integration tests, static analysis, fuzzing, coverage, benchmarks, security scans, and clean-room runs.

- Preserve raw data, immutable source inputs, experiment settings, random seeds, and exact numerical environments.

- Block promotion on critical vulnerability, license, secret, reproducibility, correctness, data-quality, or recovery failures.

- Package the result so another offline workstation can build, test, run, inspect, and continue the work.

Recommended Catalog-to-Skill Package

When converting an entry into an executable skill, keep the control file compact and place deterministic detail in supporting resources:

- SKILL.md: precise trigger description, workflow, decision rules, permissions, failure conditions, validation, and completion behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic offline builds, migrations, tests, scanners, benchmarks, validators, package tools, and recovery utilities.

- references/: schemas, compatibility matrices, architecture rules, threat models, benchmark rubrics, license guidance, and troubleshooting.

- assets/: permitted templates, fixtures, sample projects, test datasets, lockfiles, manifests, and reference outputs.

Final Acceptance Standard

A future implementation should be considered complete only when it installs and runs without network access, resolves dependencies from approved local repositories, builds reproducibly, passes correctness and security checks, records software and data provenance, survives tested failures, restores from backup, and can be rebuilt and used from a clean room by the intended recipient.
