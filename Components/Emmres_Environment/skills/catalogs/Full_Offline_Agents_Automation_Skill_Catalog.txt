Catalog edition: November 2026

Purpose and Scope

This document is a planning catalog for future reusable skills. It does not implement the listed skills. Each entry is designed so a stronger agent can later convert it into a standalone skill or a coordinated module. The target environment is fully offline or air-gapped, with local model weights, explicit permissions, durable state, deterministic validation, strong recovery, and auditable handoff.

Design Principles for Future Skill Builders

- Default to local execution, least privilege, network denial, explicit data scope, and reversible actions.

- Treat prompts, models, tools, schemas, policies, workflows, datasets, and infrastructure as versioned production dependencies.

- Use durable state, idempotency, checkpoints, and compensation for any long-running or consequential workflow.

- Require evidence-grounded answers, explicit abstention, deterministic validation, and human approval where consequences are material.

- Use security scanning and isolation before untrusted content, code, packages, models, or artifacts reach privileged tools.

- Test normal, boundary, adversarial, failure, recovery, privacy, permission, and clean-state conditions.

- Block release when critical authorization, grounding, safety, recovery, audit, or package-completeness checks fail.

Recommended Catalog-to-Skill Package

When converting an entry into an executable skill, keep the control plane compact and place repeatable detail in supporting resources:

- SKILL.md: precise trigger description, workflow, decision rules, permissions, failure conditions, validation, and completion behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic offline automation, adapters, validators, evaluators, migrations, smoke tests, and recovery tools.

- references/: schemas, policies, threat models, benchmark rubrics, compatibility matrices, runbooks, and troubleshooting.

- assets/: permitted templates, fixtures, test datasets, reference traces, configuration samples, and offline packages.

Final Acceptance Standard

A future implementation should be considered complete only when it runs without network access, declares dependencies and authority, preserves durable state and rollback, enforces permissions and budgets, grounds factual output, survives tested failures, records provenance and audit evidence, and can be installed, operated, evaluated, recovered, and continued from a clean offline package.
