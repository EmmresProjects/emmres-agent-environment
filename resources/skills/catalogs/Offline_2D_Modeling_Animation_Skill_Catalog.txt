A capability blueprint for an air-gapped creative agent covering drawing, design, animation, rigging, audio, neural generation, export, validation, licensing, automation, and clean handoff.

Catalog edition: November 2026

Purpose and Scope

This catalog defines reusable skills for a fully offline 2D modeling and animation agent. It is a planning catalog only. Each entry describes one focused capability that can later become an independent skill or a module in a coordinated skill suite. The catalog is application-neutral, but it is designed to work with installed tools such as Krita, Inkscape, Aseprite, OpenToonz, Synfig Studio, Blender Grease Pencil, FFmpeg, and equivalent offline software.

Design Rules for Future Skill Builders

- Keep every skill deterministic where possible: explicit inputs, outputs, settings, versions, paths, and validation rules.

- Prefer editable sources and reversible operations before flattened or destructive outputs.

- Assume no internet connection at execution time. Bundle permitted dependencies, documentation, models, licenses, and fallback procedures.

- Require clean-state tests on a second folder or workstation profile before declaring a bundle portable.

- Keep model, asset, font, plugin, and codec rights visible throughout the workflow.

- Treat visual review as a required gate, not as a substitute for structural and technical validation.

- Use manifests and relative paths so work can be reproduced, moved, archived, and resumed.

Recommended Catalog-to-Skill Packaging Pattern

When converting an entry into an executable skill, use a compact control file plus only the resources that improve reliability:

- SKILL.md: trigger description, workflow, decision rules, required checks, and handoff behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic offline automation for fragile or repeated steps.

- references/: schemas, naming rules, compatibility matrices, license guidance, and troubleshooting.

- assets/: permitted templates, sample projects, palettes, brushes, fonts, icons, or test fixtures.

Final Acceptance Standard

A future implementation should be considered complete only when it works without network access, declares all required inputs and dependencies, produces editable and final outputs, records provenance and versions, passes technical and visual validation, handles recoverable failures, and can be reopened or rebuilt from a clean offline bundle.
