Catalog edition: November 2026

Purpose and Scope

This document is a planning catalog for future reusable skills. It does not implement the listed skills. Each entry is scoped so a stronger agent can convert it into a standalone skill or coordinated module. The target environment is fully offline or air-gapped, with local models, licensed libraries, editable sessions, measured validation, explicit consent, auditable rights, and clean-state handoff.

Design Principles for Future Skill Builders

- Preserve untouched source recordings and editable sessions before destructive restoration, rendering, conversion, or mastering.

- Treat sample rate, bit depth, timebase, channel order, loudness, true peak, naming, metadata, and rights as shared production contracts.

- Use local models only with recorded versions, hashes, settings, licenses, consent, provenance, and artifact review.

- Validate by listening and measurement. A successful render or inference command is not proof of acceptable audio.

- Use deterministic scripts for batch conversion, loudness, metadata, stems, transcripts, checksums, and package validation.

- Test plugin recall, codec round trips, clean-state reopening, offline-only operation, and recipient playback.

- Block release on critical consent, licensing, clipping, sync, channel, loudness, corruption, or package-completeness defects.

Recommended Catalog-to-Skill Package

When converting an entry into an executable skill, keep the core control file compact and place repeatable detail in supporting resources:

- SKILL.md: precise trigger description, workflow, decision rules, rights, consent, failure conditions, validation, and completion behavior.

- agents/ui_metadata.yaml: display name, short description, icon, and brand color.

- scripts/: deterministic offline audio processing, analysis, metadata, validation, batch, packaging, and recovery tools.

- references/: standards, signal-flow diagrams, codec matrices, loudness targets, plugin maps, rights guidance, and troubleshooting.

- assets/: permitted templates, presets, test tones, impulse responses, example sessions, fixtures, and evaluation clips.

Final Acceptance Standard

A future implementation should be considered complete only when it operates without network access, declares dependencies and rights, preserves sources and rollback, measures and listens to outputs, passes clean-state and recipient playback tests, records model and processing provenance, and provides complete editable, master, stem, transcript, metadata, license, and recovery materials required by the workflow.
