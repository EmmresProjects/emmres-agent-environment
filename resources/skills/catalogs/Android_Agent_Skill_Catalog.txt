Use and Safety Boundary

- This catalog is for applications, devices, data, services, and assets that the operator owns or is explicitly authorized to inspect, modify, test, preserve, or migrate.

- Preserve original signed artifacts before modification. Never claim update compatibility without the correct signing identity or an authorized rotation path.

- Never claim true 64-bit support unless a genuine arm64-v8a library exists and has been tested on a suitable device. The Android NDK cannot convert a closed-source 32-bit library into a true 64-bit implementation.

- Separate installation success from runtime compatibility, and separate offline local behavior from functions that require retired or unavailable servers.

- Do not bypass authentication, purchases, DRM, licensing, device integrity, certificate protections, or private storage controls. Use mock services and instrumentation only for owned or explicitly authorized systems.

Appendix C. Standard Skill Contract

Purpose: One narrow outcome stated in operational terms.

Authorized scope: Ownership or explicit permission, package, device, account, network, data, and time boundaries.

Inputs: Artifacts, source, device specification, tool versions, credentials channel, and expected behavior.

Outputs: Human report, machine-readable JSON, transformed artifact, logs, hashes, and next routing decision.

Dependencies: Required tools, versions, licenses, device, network, credentials, host features, and disk or memory budget.

Side effects: Files created or changed, device state, installed packages, network calls, keys used, and cleanup requirements.

Failure statuses: FOUND, MISSING, WRONG VERSION, BROKEN, LICENSE REQUIRED, DEVICE REQUIRED, NETWORK REQUIRED, or HOST FEATURE REQUIRED, plus task-specific failures.

Verification: Fixture smoke test, output validation, clean-state rerun, device installation when relevant, launch, logs, and regression comparison.

Recovery: Preserve the last passing artifact, isolate the earliest bad state, make one reversible repair, and rerun affected checks.

Safety gate: Require explicit approval before destructive, privacy-sensitive, credentialed, signing-key, or scope-expanding actions.

Appendix E. Completion Rules

- An executable skill is not complete because a binary exists. It must pass a version check and a minimal lawful fixture.

- Every transformation preserves the original, identifies exact inputs and outputs, records hashes, and validates the artifact consumed by the next stage.

- Any APK rebuild follows decode, explicit patch, rebuild, zipalign, sign, verify, install, launch, log collection, and behavior comparison.

- Any compatibility claim names the API, ABI, device or emulator, package version, signature state, and observed test result.

- Any network or service conclusion distinguishes local app defects from remote availability, credentials, TLS, policy, and retired-service conditions.

- Any partial result states what passed, what is blocked, the exact missing dependency, and the safest continuation point.
